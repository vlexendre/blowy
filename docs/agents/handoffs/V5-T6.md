## Décisions
- **Mutations** : `AdminCommandRunner.run` (permission → step-up → CommandBus → AuditLog dans la même transaction) ; l'état des sorties n'est écrit que par `outings` via le port, dans cette transaction. Décisions de E (« je connais quelqu'un », prise en charge d'alerte) : `delegate` (audit après succès, patron existant).
- **Besoin d'aide** : file triée ouvertes d'abord / échéance la plus proche, `priority: 1`, échéance 1 h (port de E). Détail avec position = permission `safety.position` (trust_lead seulement), justification ≥ 10 car. passée à E qui audite la lecture (motif, jamais la position).
- **Vues ops** : prénoms, statuts, fiabilité « N sur M », chronologie, rapport de composition **agrégats numériques seulement** ; aucun montant (`refundState` seulement si `economy.read`), aucun vote, préférence, `friendsOnly`.
- **Contestation acceptée** : no-show → présent·e (check-in `STAFF`), compteurs corrigés, pause levée si en cours, trace `ReliabilityEvent(…:staff-correction)`, outbox `outing.attendance_corrected`, compensation lieu contre-passée (`reverseVenueCompensation` de G) — même transaction.
- **Lieu partenaire = royaume distinct**, pas un rôle staff : clé HMAC dérivée (`blowy:venue-partner:v1`), secret TOTP dérivé de `venue:<userId>`, anti-rejeu propre, sessions `DeviceSession(platform='venue-partner')`, CSRF lié, cookies `blowy_venue*`, révocation immédiate au retrait d'accès. Session staff / bearer mobile refusés (testé).
- **Effectif** : prénoms (premier mot du nom affiché) à partir de `lockAt` et seulement pour les places confirmées ; nombre avant ; code du chevalet dès la confirmation ; schéma `.strict()` à la sortie. Illustrations des lignes **décoratives par position**, jamais le pet de la personne (§3.2 : le lieu ne voit pas les pets).
- **Créneaux** : planning = créneaux types de la ville × activités du lieu ; jour fermé / tables par jour / plafond / fermetures appliqués aux `VenueSlot` sur 3 semaines (lignes à capacité 0 qui bloquent le générateur, `skipDuplicates`) ; une baisse ne touche pas un créneau à moins de 72 h ; **fermeture exceptionnelle** → sorties du jour annulées `VENUE_UNAVAILABLE` (remboursées) + audit `venue.closure_cancelled_outings` (`opsAttention`).
- **Compensations** : relevé mensuel lieu agrégé par sortie (aucun prénom, aucun financement individuel) ; vue finance avec contre-passation (step-up).
- **Astreinte** : `VENUE_ONCALL_PHONE` ; numéro de démo seulement en local/test, sinon « Numéro à venir » (jamais inventé).

## Limites
- Écritures quartiers/lieux/créneaux faites par l'adapter admin (configuration sans invariant de jeu) : port `neighborhoods` à fournir par C.
- Les générateurs de créneaux (`neighborhoods.generate_slots`, `ensureVenueSlots`) ignorent la politique du lieu : couverte par la matérialisation 3 semaines + job quotidien.
- Un compte partenaire multi-lieux voit le premier lieu dans l'UI (l'API accepte `?venueId=`).
- « Changer la photo » = demande à l'équipe (aucun téléversement) ; l'URL validée est posée par ops.
- `PAUSED`/`CLOSED` d'un quartier n'annule pas les sorties déjà composées.
- La fixture e2e simule la confirmation (SQL) et ajoute brunch/bloc aux activités du lieu de démo pour reproduire la maquette.
- Justification de lecture de position transmise en paramètre d'URL (même patron que le contexte de dossier).
