## Décisions
- **Jeton** : 32 o aléatoires → base64url (43 car.) ; seule l'empreinte SHA-256 est stockée. Le résultat mémorisé par le CommandBus ne contient **jamais** le jeton : un rejeu de la même clé renvoie 409 `GUARDIAN_LINK_ALREADY_ISSUED` (l'URL perdue n'est pas ré-émise ; révoquer et recréer). Testé (aucune occurrence du jeton dans `CommandRecord`).
- **Page du proche** : prénom, type, date/heure, lieu dès le verrouillage (place confirmée), chronologie `CHECKED_IN`/`OK`/`ALERT`/`ENDED`, numéros 112/17, `expiresAt`. Jamais d'autre participant, chat, fiabilité, Blowy+, **ni position (V5.3 A.4)**. Une alerte ouverte est toujours montrée, même hors fenêtre. 404 identique (inconnu, mal formé, révoqué, expiré, place annulée/retirée, sortie annulée). `no-store`, `noindex`, `no-referrer`, aucune IP ni empreinte (compteur de vues seul).
- **Alerte** : jamais refusée sauf > 10/h (429 avec 112/17) ; dossier `SAFETY_ALERT` priorité 1, échéance = création + 60 min (« réponse humaine < 1 h » affichée via `humanResponseMinutes` et `GET /safety/status.support`) ; position facultative réservée au staff (trust_lead/admin, lecture justifiée et auditée), purgée 72 h, retenue tant que le dossier est ouvert ; la position n'entre jamais dans l'empreinte d'idempotence. Résolution « SAFE » par la personne : la page affiche « tout va bien », le dossier reste ouvert pour le suivi staff.
- **Créneaux de réponse humaine** = fenêtre active de la sortie (`startsAt − 2 h` → `endsAt + 3 h`) ; `staffedNow` en dépend.
- **Web Push** : notifications sans contenu (VAPID RFC 8292, pas de charge → aucune clé d'abonnement stockée, seul l'endpoint, purgé à expiration + 24 h). Stratégie : VAPID si configuré ; enregistreur local hors production ; désactivé en production sans clés (501, page toujours consultable). Le design promettait SMS/appel au proche : **non retenu** (Blowy ne stocke ni numéro ni email du proche, spec §2.9) ; la page dit « cette page passe au rouge ».
- **Retrait système (D-025)** : dans la transaction du blocage (ordre users → pets → relationships → outings), la personne bloquée quitte toute sortie active partagée via le port outings (remboursement par `SeatFundingPort` d'economy, `cancelKind=SYSTEM_REMOVAL`, aucune fiabilité, révocation chat/salle WS, « ne pourra pas venir » pour le groupe). Trace `SafetySystemRemoval` ; dossier `SYSTEM_REMOVAL_ABUSE_SIGNAL` au-delà de `[T] safety.removalAbuseThreshold` retraits en 30 j ; notification neutre via `outing.composition_changed` (T8).
- **« Je connais quelqu'un »** (C, T2) : le cas `IN_REVIEW` ouvre un dossier `OUTING` (sujet = place, priorité 1, échéance 1 h) ; décision staff `resolveKnowsSomeone` : accepté → retrait sans pénalité (si la sortie n'a pas commencé), refusé → place gardée ; dossier clos.
- **Visages** : ACL existante `OUTING_REVEAL` (participant·es confirmé·es, `photoRevealAt = startsAt − 3 h` via tuning, jusqu'à la clôture des votes) ; jeton court 5 min ; **filigrane serveur** du prénom du regardeur (faisable avec sharp/librsvg, testé). Le blocage « capture d'écran » reste côté mobile (D).
- **Consentement art. 9** : déjà livré par C (`SENSITIVE_PREFERENCES` requis pour `romanceGenders`, retrait = effacement dans la même transaction) ; vérifié par test d'intégration (403 sans consentement, purge au retrait, re-403 ensuite). `meetGenders` (amis) n'est pas soumis à ce consentement (documenté).
- **Incident sur place** : sans personne visée → `SafetyIncident` (le `Report.reportedUserId` est NOT NULL et consommé par matching/outings : pas modifié).
